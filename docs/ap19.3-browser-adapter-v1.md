# AP19.3 – HeldenMobil Browseradapter V1

Stand: 2026-09-14

## Ziel

AP19.3 setzt den in AP19.2 definierten Vertrag auf einen kleinen, gekapselten Browserkanal. Der Adapter kennt weder das DOM noch `app.js`, HLD-XML, OneDrive noch Companion-Persistenz.

Er darf ausschließlich mit einem **explizit registrierten Provider** arbeiten.

## Sicherheits- und Kopplungsregeln

1. **Kein Wildcard-Origin.** `*` ist in `allowedOrigins` ausdrücklich verboten.
2. **Fail closed.** Nachrichten nicht freigegebener Origins werden ohne Antwort ignoriert.
3. **Antwort nur an die konkrete Request-Origin.** `postMessage` verwendet niemals `*`.
4. **Capability-Gate.** Jede fachliche Operation benötigt eine explizit aktivierte und vom Provider tatsächlich angebotene Capability.
5. **Kein Provider = keine Heldendaten.** Der Adapter liest nichts selbst aus dem Browser oder aus dem HeldenMobil-DOM.
6. **Kein direkter Import aus `app.js`.** `bridge-browser-adapter.js` kennt nur `bridge-contract-v1.js`.
7. **Vertrag vor Provider.** Eingehende Requests und ausgehende Resultate werden gegen AP19.2 validiert.
8. **Antwortkorrelation.** Ein Provider darf kein Ergebnis für eine andere Request-/Hero-ID zurückgeben.

## Transport

V1 verwendet gekapseltes `window.postMessage`.

Kanal:

```text
heldenmobil-dsa41-bridge
```

Transportversion:

```text
1
```

Request-Hülle:

```json
{
  "channel": "heldenmobil-dsa41-bridge",
  "version": 1,
  "messageId": "maze:request:42",
  "type": "check.execute",
  "payload": {}
}
```

Response-Hülle:

```json
{
  "channel": "heldenmobil-dsa41-bridge",
  "version": 1,
  "replyTo": "maze:request:42",
  "type": "check.execute.result",
  "payload": {},
  "error": null
}
```

## Capabilities

V1 kennt:

- `hero:list`
- `hero:snapshot:v1`
- `check:execute:v1`
- vorbereitend `combat:execute:v1`

Eine Capability wird nur angeboten, wenn **beides** gilt:

- sie ist in `allowedCapabilities` freigegeben und
- der registrierte Provider besitzt die dazugehörige Funktion.

Ein `bridge.hello` verhandelt die Schnittmenge zwischen angefragten und tatsächlich verfügbaren Capabilities.

## Nachrichten

### `bridge.hello`

Discovery/Handshake. Liefert Produkt, Transportversion, Contract-Version und ausgehandelte Capabilities.

### `hero.list`

Liefert nur eine schmale Liste aus `heroId`, Name und Capabilities. Keine vollständigen Heldendaten.

### `hero.get`

Liefert genau einen validierten `HeroSnapshotV1`.

### `check.execute`

Nimmt einen validierten `CheckRequestV1`, ruft den Provider auf und akzeptiert nur einen korrelierenden `CheckResultV1` mit gleicher `requestId` und `heroId`.

### `combat.execute`

Ist bereits technisch vorgesehen, bleibt aber eine vorbereitete Capability für spätere Kampf-APs.

## Provider-Grenze

Der Adapter erwartet bei Bedarf ein Objekt mit schmalen Funktionen:

```text
listHeroes()
getHeroSnapshot(heroId)
executeCheck(checkRequestV1)
executeCombat(combatActionV1)   // optional/vorbereitet
```

Diese Funktionen sind die einzige Stelle, an der der Adapter HeldenMobil-Fachdaten erhalten darf.

Der laufende Lab-Monolith muss seinen Provider später **explizit registrieren**. Der Adapter darf weder private `state`-Variablen auslesen noch DOM-Tabellen zurückparsen oder IndexedDB/LocalStorage durchsuchen.

## Fehlerverhalten

Autorisierte Requests können strukturierte Fehler erhalten:

- `UNSUPPORTED_TRANSPORT_VERSION`
- `CAPABILITY_UNAVAILABLE`
- `PROVIDER_UNAVAILABLE`
- `UNSUPPORTED_MESSAGE_TYPE`
- `PROVIDER_ERROR`

Nicht autorisierte Origins erhalten bewusst **keine** Antwort.
