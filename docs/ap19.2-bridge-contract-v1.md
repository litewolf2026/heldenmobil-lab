# AP19.2 – Gemeinsamer Bridge-Vertrag V1

Stand: 2026-09-14

## Ziel

AP19.2 definiert die stabile, versionierte Datengrenze zwischen Shared Maze und HeldenMobil, **bevor** in AP19.3 ein Browsertransport gebaut wird.

Der Vertrag ist transportneutral. `postMessage`, `BroadcastChannel`, Origin-Gates, Discovery und Timeouts gehören erst in AP19.3/AP19.4.

## Autoritätsgrenze

Die wichtigste Regel lautet:

> Shared Maze beschreibt **was geprüft werden soll und warum**. HeldenMobil bestimmt **mit welchen Heldendaten und DSA-Regeln** die Probe ausgeführt wird.

Damit darf ein `CheckRequestV1` insbesondere **keinen TaW/ZfW, keine AT/PA-Werte und keine normativen Eigenschaftswerte** aus Shared Maze mitbringen.

Beispiel:

```json
{
  "schema": "CheckRequestV1",
  "version": 1,
  "requestId": "req:maze:17",
  "heroId": "hero:123",
  "check": {
    "kind": "talent",
    "key": "Sinnesschärfe",
    "label": "Sinnesschärfe",
    "mode": "standard"
  },
  "modifier": 3,
  "modifiers": [
    {"source": "shared-maze", "value": 3, "reason": "verborgene Falle", "kind": "difficulty"}
  ],
  "context": {
    "source": "shared-maze",
    "entityRef": "trap:17",
    "hiddenRoll": true
  }
}
```

HeldenMobil löst dazu selbst den konkreten Helden, Talentwert und das 3W20-Eigenschaftstriple auf.

## Vertragsobjekte

### `HeroSnapshotV1`

Read-only Snapshot eines Helden für andere Produkte.

Enthält mindestens:

- stabile `heroId`,
- Name,
- Eigenschaften,
- aktuelle/maximale Energien,
- Talente mit Wert und Probe,
- Zauber mit ZfW/Probe/Repräsentation/Komplexität soweit vorhanden,
- relevante abgeleitete Kampfwerte,
- optionale Capabilities und Darstellungsmetadaten.

Nicht enthalten werden interne HLD/XML-Strukturen, Companion-Persistenz, OneDrive-Daten oder UI-Zustand.

### `CheckRequestV1`

Beschreibt eine gewünschte Probe:

- `requestId`,
- `heroId`,
- Check-Art (`attribute`, `talent`, `spell`, `liturgy`, vorbereitend auch `attack`, `parry`, `ranged`),
- fachlicher Schlüssel, z. B. `Sinnesschärfe`,
- Gesamtmodifikator,
- nachvollziehbare Modifikatorliste,
- Kontext/Grund/Referenzen.

Die Modifikatorliste dient Transparenz. `modifier` bleibt der effektive Gesamtwert, damit einfache Clients nicht selbst Modifikatoren aggregieren müssen.

### `CheckResultV1`

Strukturiertes Ergebnis:

- gleiche `requestId` und `heroId`,
- Check-Art,
- Status (`resolved`, `cancelled`, `unsupported`, `error`),
- Erfolg/Misserfolg bei aufgelöster Probe,
- Ergebnisart (`success`, `critical-success`, `fumble`, ...),
- TaP*/ZfP*/LkP* als `qualityPoints`, soweit vorhanden,
- Würfe und Zielwerte,
- effektiver Regelwert,
- angewandte Modifier,
- generische `Effect[]`,
- `ResourceDeltaV1[]`,
- optionale Anzeige-/Diagnosedaten.

Unmodellierte **Wirkungen** machen eine erfolgreich ausgeführte Probe nicht automatisch `unsupported`: Die Probe kann `resolved` sein und einen `manual`-Effect liefern.

### `ResourceDeltaV1`

Beschreibt eine vorgeschlagene oder erlaubte Ressourcenänderung.

Wichtig: Ein nicht erlaubter Ressourcenverbrauch wird **nicht still gekappt**.

Beispiel AsP 5 bei Kosten 7:

```json
{
  "schema": "ResourceDeltaV1",
  "version": 1,
  "resource": "AsP",
  "current": 5,
  "delta": -7,
  "next": 5,
  "allowed": false,
  "reason": "zu wenig AsP",
  "source": "magic-core"
}
```

Damit kann der spätere Browseradapter Vorschau → Bestätigung → Commit sauber trennen.

### `CombatActionV1` / `CombatResultV1`

Diese beiden Verträge werden in AP19.2 bereits vorbereitet, aber noch nicht als vollständiges Kampfsystem festgeschrieben.

`CombatActionV1` transportiert generisch:

- Aktion/Actor/Held,
- optionales Ziel,
- optionale Waffenreferenz,
- Manöverliste,
- Modifikator,
- Kontext,
- erweiterbares Payload.

`CombatResultV1` kann anschließend einen normalen `CheckResultV1`, Effects und ResourceDeltas enthalten.

Dadurch muss die Bridge später nicht für Wuchtschlag, Finte, Hammerschlag oder einzelne Zauber neue Nachrichtentypen erfinden.

## Generische Effects

AP19.1b hat bereits folgende Effect-Typen festgelegt:

- `modifier`
- `damage`
- `heal`
- `resource`
- `state`
- `manual`

Der Bridge-Vertrag übernimmt genau diese generische Form. Einzelne Zauber/SF sind **keine Vertragsfelder**.

Beispiele:

- ARMATRUTZ kann später `modifier`/`state` liefern,
- FULMINICTUS `damage`,
- BALSAM `heal` + `resource`,
- noch nicht automatisierter Zauber `manual`.

## Anschluss an die bestehende Shared-Maze-Naht

Shared Maze erzeugt heute bereits das Browserereignis `maze-check-request` mit:

```text
entity + action + check
```

Das bisherige `check` enthält u. a. Namen, Modifier, Gründe und teilweise ein Eigenschaftstriple.

Für AP19.4 gilt die geplante Abbildung:

| heutiges Shared-Maze-Feld | Bridge V1 | Autorität |
| --- | --- | --- |
| `check.name` | `check.key` / `check.label` | Shared Maze fordert die Probe an |
| `check.modifier` | `modifier` | Shared Maze liefert situative Schwierigkeit |
| `check.reason` | `context.reason` | Shared Maze |
| `hiddenRoll` | `context.hiddenRoll` | Shared Maze/SL-Darstellung |
| `attributes` | höchstens `context.advisoryAttributes` | **nicht normativ** |
| TaW/ZfW/Heldenwerte | werden nicht übertragen | **HeldenMobil** |

Damit bleibt `maze-check-request` die Integrationsnaht, wird aber nicht zur zweiten DSA-Regelquelle.

## Versions- und Fehlerverhalten

- jedes Vertragsobjekt trägt `schema` und `version`,
- V1 akzeptiert nur `version: 1`,
- unbekannte Schemas/Versionen fail-closed,
- unbekannte Check-Arten fail-closed,
- nicht unterstützte fachliche Probe wird explizit als `status: unsupported` zurückgegeben,
- Browsertransportfehler werden erst in AP19.3/AP19.4 modelliert.
